# 热度排序后端API修复方案

## 问题分析

当前文章列表API不返回pv/uv字段，导致前端热度排序无法使用真实的浏览量数据。

### 现状
- **文章详情API**: 实时计算并返回pv/uv字段
- **文章列表API**: 只返回基本字段，不包含访问统计

## 解决方案

### 方案A：性能优化版（推荐）

在列表API中添加可选的访问统计计算：

```typescript
// server/src/services/feed.ts 修改建议

// 在第91-100行的map函数中添加pv/uv计算
.map(async ({ content, hashtags, summary, ...other }) => {
    const avatar = extractImage(content);
    
    // 可选：计算访问统计（仅在需要热度排序时）
    let pv = 0, uv = 0;
    if (query.includeStats === 'true') {
        const visit = await db.query.visits.findMany({
            where: eq(visits.feedId, other.id),
            columns: { id: true, ip: true }
        });
        pv = visit.length;
        uv = new Set(visit.map((v) => v.ip)).size;
    }
    
    return {
        summary: summary.length > 0 ? summary : markdownToPlainText(content, 150),
        hashtags: hashtags.map(({ hashtag }) => hashtag),
        avatar,
        pv,
        uv,
        ...other
    }
})
```

### 方案B：缓存优化版

使用Redis缓存访问统计数据：

```typescript
// 添加访问统计缓存
const getVisitStats = async (feedId: number) => {
    const cacheKey = `visit_stats_${feedId}`;
    const cached = await cache.get(cacheKey);
    
    if (cached) {
        return JSON.parse(cached);
    }
    
    const visit = await db.query.visits.findMany({
        where: eq(visits.feedId, feedId),
        columns: { id: true, ip: true }
    });
    
    const stats = {
        pv: visit.length,
        uv: new Set(visit.map((v) => v.ip)).size
    };
    
    // 缓存5分钟
    await cache.set(cacheKey, JSON.stringify(stats), 300);
    return stats;
};
```

## 性能考虑

1. **按需计算**: 仅在热度排序时计算pv/uv
2. **缓存策略**: 使用Redis缓存统计数据
3. **批量查询**: 使用JOIN优化数据库查询
4. **异步更新**: 统计数据可以异步更新

## 实施建议

1. **第一阶段**: 实施方案A，添加可选的统计计算
2. **第二阶段**: 根据性能表现，考虑添加缓存（方案B）
3. **第三阶段**: 如果访问量很大，考虑冗余字段（方案C）

## 兼容性

- 保持现有API的向后兼容性
- 通过查询参数控制是否返回统计数据
- 不影响现有的文章详情API逻辑
